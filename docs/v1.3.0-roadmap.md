> **P1–P4 are ALL COMPLETE.**

> - **P2 (Server-Initiated Notifications)** — shipped in v1.4.0
> - **P3 (Resource Subscriptions)** — shipped in v1.4.0
> - **P4 (Resource Templates)** — shipped in v1.4.0

## Goal

Implement SSE (Server-Sent Events) streaming responses, server-initiated
notifications, resource subscriptions, and resource templates for the
Streamable HTTP transport, bringing AegisGate MCP to full compliance with
the MCP 2025-06-18 spec for Streamable HTTP.

## Background

v1.2.2 implemented the request/response mode of Streamable HTTP with proper
session management (`Mcp-Session-Id`). The spec also defines a streaming mode
where the server responds with `text/event-stream` and can push multiple
messages over a single HTTP connection. This is important for:

- Long-running tool calls that stream progress
- Server-initiated notifications (list changed, resource updated)
- Batch responses to requests

## Scope

### P1: SSE Streaming Responses ✅ COMPLETE (v1.3.0)

When a client sends a POST with `Accept: text/event-stream`, the server
responds with `Content-Type: text/event-stream` and streams JSON-RPC
responses as SSE events.

**Implemented:**
1. Check `Accept` header in `handleMCP` — if it includes `text/event-stream`,
   switch to streaming mode
2. Set `Content-Type: text/event-stream` and `Cache-Control: no-cache`
3. Flush each JSON-RPC response as an SSE event: `data: {json}\n\n`
4. For notifications (no response), send a comment line `: ack\n\n`
5. Keep the connection open for server-initiated messages

### P2: Server-Initiated Notifications ✅ COMPLETE (v1.4.0)

Implemented `notifications/*list_changed` and `notifications/resources/updated`
so the server can proactively notify clients when:

- A tool is registered or removed → `notifications/tools/list_changed`
- A resource is registered or removed → `notifications/resources/list_changed`
- A prompt is registered or removed → `notifications/prompts/list_changed`
- A resource's content changes → `notifications/resources/updated`

**Implemented:**
1. `listChanged: true` in capability advertisements
2. `NotificationCallback` type for transport-layer notification delivery
3. `NotifyToolsListChanged()`, `NotifyResourcesListChanged()`, `NotifyPromptsListChanged()` on `SecuredMCPServer`
4. `NotifyListChanged()` and `NotifyResourceUpdated()` on `RequestHandler`
5. `makeNotificationCallback()` on Streamable HTTP transport for SSE delivery
6. `currentSessionID` thread-local for subscription tracking

### P3: Resource Subscriptions ✅ COMPLETE (v1.4.0)

Implemented real `resources/subscribe` and `resources/unsubscribe`:

1. Per-session subscription tracking (`map[string]map[string]bool`)
2. On `resources/subscribe`, validate resource exists, add session to subscription list
3. On `resources/unsubscribe`, remove it (idempotent)
4. When a resource's content changes (via `NotifyResourceUpdated`), send
   `notifications/resources/updated` to all subscribed sessions
5. `subscribe: true` advertised in resources capability

### P4: Resource Templates ✅ COMPLETE (v1.4.0)

Implemented `resources/templates/list` for parameterized resources:

```json
{
  "uriTemplate": "file:///projects/{projectName}/docs/{docName}",
  "name": "Project Documentation",
  "description": "Documentation for a specific project"
}
```

**Implemented:**
1. `ResourceTemplate` type in `types.go`
2. `RegisterTemplate()` and `ListTemplates()` on `ResourceRegistry`
3. `resources/templates/list` handler
4. `RegisterResourceTemplate()` on `SecuredMCPServer`

## Out of Scope (v1.5.0+)

- `elicitation/create` (server-initiated information requests from client)
- `completion/complete` (full autocompletion implementation)
- `Last-Event-ID` reconnection with replay
- Per-session SSE stream multiplexing
