# AegisGate MCP v1.3.0 Roadmap — SSE Streaming & Event Notifications

## Goal

Implement SSE (Server-Sent Events) streaming responses and server-initiated
notifications for the Streamable HTTP transport, bringing AegisGate MCP to
full compliance with the MCP 2025-06-18 spec for Streamable HTTP.

## Background

v1.2.2 implemented the request/response mode of Streamable HTTP with proper
session management (`Mcp-Session-Id`). The spec also defines a streaming mode
where the server responds with `text/event-stream` and can push multiple
messages over a single HTTP connection. This is important for:

- Long-running tool calls that stream progress
- Server-initiated notifications (list changed, resource updated)
- Batch responses to requests

## Scope

### P1: SSE Streaming Responses

When a client sends a POST with `Accept: text/event-stream`, the server
should respond with `Content-Type: text/event-stream` and stream JSON-RPC
responses as SSE events.

**Implementation:**
1. Check `Accept` header in `handleMCP` — if it includes `text/event-stream`,
   switch to streaming mode
2. Set `Content-Type: text/event-stream` and `Cache-Control: no-cache`
3. Flush each JSON-RPC response as an SSE event: `data: {json}\n\n`
4. For notifications (no response), send a comment line `: ack\n\n`
5. Keep the connection open for server-initiated messages
6. Support `Last-Event-ID` header for reconnection (optional, P2)

**Files to modify:**
- `streamable_http.go` — Add SSE response writer, Accept header negotiation
- `handler.go` — No changes needed (handler returns response, transport decides how to send)

**Estimated effort:** 4-6 hours

### P2: Server-Initiated Notifications

Implement `notifications/*list_changed` and `notifications/resources/updated`
so the server can proactively notify clients when:

- A tool is registered or removed → `notifications/tools/list_changed`
- A resource is registered or removed → `notifications/resources/list_changed`
- A prompt is registered or removed → `notifications/prompts/list_changed`
- A resource's content changes → `notifications/resources/updated`

**Implementation:**
1. Re-enable `listChanged: true` in capability advertisements
2. Add notification dispatch to active SSE connections
3. `ToolRegistry.Register()` → trigger `notifications/tools/list_changed`
4. `ResourceRegistry.Register()` → trigger `notifications/resources/list_changed`
5. `PromptRegistry.Register()` → trigger `notifications/prompts/list_changed`
6. Add `ResourceRegistry.NotifyUpdated(uri string)` for content changes
7. Need a connection registry in the transport to broadcast notifications

**Files to modify:**
- `streamable_http.go` — SSE connection tracking, notification broadcasting
- `handler.go` — Re-enable capability advertisements
- `secured_server.go` — Wire notification triggers to registry methods

**Estimated effort:** 6-8 hours

### P3: Resource Subscriptions

Re-implement `resources/subscribe` and `resources/unsubscribe` with real
functionality:

1. Track which clients are subscribed to which resource URIs
2. On `resources/subscribe`, add the session to the subscription list for that URI
3. On `resources/unsubscribe`, remove it
4. When a resource's content changes (via `NotifyUpdated`), send
   `notifications/resources/updated` to all subscribed sessions
5. Re-enable `subscribe: true` in the resources capability advertisement

**Files to modify:**
- `handler.go` — Real subscribe/unsubscribe handlers
- `streamable_http.go` — Subscription tracking, notification delivery
- `v120_test.go` or new `v130_test.go` — Tests

**Estimated effort:** 4-6 hours

### P4 (optional): `resources/templates/list`

Implement URI templates for parameterized resources:

```json
{
  "uriTemplate": "file:///projects/{projectName}/docs/{docName}",
  "name": "Project Documentation",
  "description": "Documentation for a specific project"
}
```

**Estimated effort:** 3-4 hours

## Out of Scope (v1.4.0+)

- `elicitation/create` (server-initiated information requests from client)
- `completion/complete` (full autocompletion implementation)
- `Last-Event-ID` reconnection with replay
- Per-session SSE stream multiplexing

## Testing Strategy

- Test SSE response format (Content-Type, event framing)
- Test streaming a single response
- Test notification delivery to active SSE connections
- Test subscription lifecycle (subscribe → update → notification → unsubscribe)
- Test session expiry during SSE connection
- Test that non-SSE clients still get request/response mode

## Release Plan

1. Create branch `feat/v1.3.0-sse-streaming`
2. Implement P1 (SSE streaming) → test → commit
3. Implement P2 (notifications) → test → commit
4. Implement P3 (subscriptions) → test → commit
5. Update README, CHANGELOG, docs
6. PR, CI, merge
7. Tag v1.3.0, release with signed artifacts
8. Submit to MCP directories

## Dependencies

None — all implementation uses Go standard library (`net/http` already supports
streaming via `Flusher` interface). No new external dependencies.
